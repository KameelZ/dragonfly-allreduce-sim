g-PAARD's own 6-step reduce-scatter + all-gather all-reduce schedule. This is the actual workload the routing in this project was built for, so it is the baseline every other pattern is judged against: if Dragonfly+ doesn't win here, the extra spine hardware isn't paying for itself on the workload that matters.

Optimization idea #2: g-PAARD with steps 3/4's flat O(hosts^2) intra-group any-to-all replaced by a 2-level hierarchy -- combine within each leaf/router first (cheap, same cost in DF and DF+), then exchange among one representative per leaf only (the only part that crosses DF+'s expensive leaf-spine hop, now O(leaves^2) instead of O(hosts^2)), then broadcast back. test_7's spine-oversubscription triage showed hardware alone can't fix the gap (no ECMP in this project's routing); this targets the same contention by cutting message volume instead.

Mininet-safe stand-in for the paper's node-count scale test: groups grow (and with them, switch/link count) while hosts/group stays fixed at the validated-safe 8, instead of growing hosts/group (which is what caused the earlier near-stall incident at 24 hosts/group).
